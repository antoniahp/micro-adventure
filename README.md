# micro-adventure

MicroAdventures: an app that nudges you outside after work with short walking challenges (touch something soft, find a singing bird, spot an old tree). Challenges are generated by an open model (Gemma through Ollama) and every walk is stored in MongoDB Atlas. This repo holds the backend (`src/`) and the web client (`web/`).

## Stack

- Python 3.12, Django 5.2, django-ninja (HTTP layer), dependencies managed with Poetry
- MongoDB Atlas through the official `django-mongodb-backend`, with regular Django models
- Ollama serving an open-weight model, for challenge generation and photo checks
- Sentry, optional

## Architecture

Hexagonal architecture with CQRS, laid out like `kronobot/backend`. One bounded context today: `microadventures`.

```
micro-adventure/
├── pyproject.toml        # Poetry
├── poetry.lock
├── src/
│   ├── manage.py
│   ├── core/             # Django settings, urls, wsgi/asgi, MongoDB AppConfigs for the admin
│   ├── mongo_migrations/ # Migrations of Django's own apps (admin, auth, contenttypes) for MongoDB
│   ├── api/              # Driving adapter: django-ninja routers, schemas, error mapping
│   │   └── wiring.py     # Builds each handler with its real adapters
│   └── microadventures/
│       ├── domain/
│       │   ├── models/       # Walk, Challenge, enums, value objects
│       │   ├── services/     # Abstract ports: WalkService, ChallengeGenerator, PhotoVerifier
│       │   └── exceptions/
│       ├── application/
│       │   ├── commands/     # start_walk, complete_challenge, swap_challenge
│       │   └── queries/      # find_walk, find_progress
│       ├── infrastructure/
│       │   ├── repositories/ # DbWalkRepository
│       │   └── api/          # Ollama calls (challenges and photo checks)
│       ├── admin.py          # Django admin for Walk
│       ├── models/           # Re-exports domain models so Django discovers them
│       └── migrations/
├── tests/                # Mirrors src/
└── web/                  # Web client: React + Vite + TypeScript (see web/README.md)
```

Dependency rule: `infrastructure` and `api` depend on `application` and `domain`; `application` depends only on `domain`. Domain models are Django models, the same trade-off kronobot makes.

### Models

- `Walk` is the aggregate: user, mood, minutes, weather, swaps used, creation time.
- `Challenge` is an embedded model stored inside its walk (`EmbeddedModelArrayField`), so a walk is read and written as one document. It has no collection of its own.
- Business rules live on the models (`Walk.swap_challenge`, `Challenge.requires_photo`), not in routers.

### Ports and adapters

| Port (in `domain/services/`) | Adapters (in `infrastructure/`) |
| --- | --- |
| `WalkService` | `DbWalkRepository` |
| `ChallengeGenerator` | `OllamaChallengeGenerator`, `TemplateChallengeGenerator`, `FallbackChallengeGenerator` |
| `PhotoVerifier` | `OllamaPhotoVerifier`, `TrustingPhotoVerifier` |

Naming rule for persistence: the abstract port in `domain/services/` is a *Service* (`WalkService`), and its concrete implementation in `infrastructure/repositories/` is a *Repository* (`DbWalkRepository`). Handlers depend on the service and receive the repository.

`FallbackChallengeGenerator` tries Ollama first and falls back to a fixed bank of challenges if the model is slow or down.

### Speed: warm-up while the person writes

The start form asks for free text ("cuéntame cómo vienes"). Writing it takes longer than loading the model, so the web client calls `POST /api/warmup` as soon as the form opens; Ollama loads Gemma into memory (`keep_alive`) while the person types. The note is stored in the walk, so swapped challenges are generated with the same context.

### Telling a challenge

Challenges are answered by telling, not only by photographing. A challenge is completed with a story (at least 10 characters), a photo that the model accepts, or both. Challenges about people never take a photo. A story can be written or recorded: the web client records a voice note, `POST /api/transcribe` turns it into text with ElevenLabs, and the person edits that text before sending it. Audio is never stored, only the final text (`Challenge.story`).

### CQRS rules

- A **command** changes state and returns nothing (`StartWalkCommand`, `CompleteChallengeCommand`, `SwapChallengeCommand`, `WarmUpGeneratorCommand`). The caller creates any ID it needs, so the API can answer with it.
- A **query** returns data and never changes state (`FindWalkQuery`, `FindProgressQuery`, `TranscribeAudioQuery`).
- Each use case lives in `application/commands/<use_case>/` or `application/queries/<use_case>/` as `<use_case>_command.py` + `<use_case>_command_handler.py` (or `_query`). Handlers receive their ports in the constructor and expose a single `handle()`.

### Adding a use case

1. Create `microadventures/application/commands/<use_case>/` (or `queries/`) with the command or query and its handler.
2. Add a builder function in `api/wiring.py`.
3. Add a route in `api/routers/` and, if it can fail, map its exception in `api/errors.py`.
4. Test the handler with the fakes in `tests/fakes.py`.

## Languages

The app is bilingual (Spanish and English). The web client picks the browser language on the first visit and remembers the choice (ES/EN switch in the top bar). The chosen language travels as `language` when a walk starts: it is stored in the walk, and Gemma (or the template fallback) writes the challenges in that language, including the ones created later by a swap. To add a language: one block in `web/src/i18n.tsx`, one entry in `Language`, one prompt in `ollama_challenge_generator.py` and one bank in `template_challenge_generator.py`.

## Measuring the model

`python3 scripts/benchmark.py` (app running) warms the model up, creates 5 walks in Spanish and 5 in English, and prints the time of each plus the median. Run it cold, warm, and against the GPU Droplet to get the numbers for the post. With `SENTRY_DSN` set, the same calls appear in Sentry with latency and tokens.

## Admin

Django admin is served at `/admin/`. It needs a superuser:

```bash
make migrate          # creates the admin/auth collections too
make createsuperuser
```

It lists walks (filter by mood or weather, search by user) and shows each walk's challenges as read-only text. The admin and auth apps use their own `AppConfig` (`core/apps.py`) and migrations (`mongo_migrations/`) because MongoDB needs ObjectId primary keys.

## API

Swagger UI is served at `/api/docs`.

| Method | Path | Use case |
| --- | --- | --- |
| POST | `/api/warmup` | Load the model; the web client calls it when the form opens |
| POST | `/api/walks` | Start a walk and generate its challenges (optional free-text `note`, which the model reads, and `language`: `es` by default or `en`) |
| GET | `/api/walks/{walk_id}` | Find a walk |
| POST | `/api/walks/{walk_id}/challenges/{challenge_id}/complete` | Complete a challenge (multipart: `story` text and/or `photo`; people challenges take a story only) |
| POST | `/api/transcribe` | Turn a voice note (multipart `audio`) into text with ElevenLabs |
| POST | `/api/walks/{walk_id}/challenges/{challenge_id}/swap` | Swap a challenge (max 2 per walk) |
| GET | `/api/users/{user_id}/progress` | Progress and stickers |
| GET | `/api/health` | Health check |

## Local development

Dependencies are managed with Poetry (`poetry install`, `poetry add <package>`, `poetry lock`). Without Docker: `poetry install`, then `cd src && python manage.py runserver`, and from the repo root `pytest`.

Requires Docker and Docker Compose, and Ollama running on the host with the model pulled (`ollama pull gemma3:latest`, or whatever tag you use).

```bash
make run      # app + local MongoDB at http://localhost:8000
make createsuperuser  # once, to log in at /admin (migrations run automatically on start)
make test     # tests; the repository tests use the compose MongoDB
```

If Ollama is not running, challenges come from the template bank. `PHOTO_VERIFIER=trusting` (the compose default) accepts every photo.

## Configuration

Settings live in `local.env` (ignored by git). The file must exist, so the first time run `make setup`, which copies `sample.env`, the committed template with every variable and no secrets. Edit `local.env` to add your `SENTRY_DSN` or `ELEVENLABS_API_KEY`, then `docker compose up -d`. `docker-compose.yml` only keeps the wiring that never changes (Mongo and Ollama addresses). On Render, set the same variables in the service's Environment tab instead.

| Variable | Default | Purpose |
| --- | --- | --- |
| `DJANGO_SECRET_KEY` | required | Django secret |
| `DEBUG` | `False` | Debug mode |
| `ALLOWED_HOSTS` | `*` | Comma-separated hosts |
| `MONGODB_URI` | `mongodb://localhost:27017` | Atlas connection string in production |
| `MONGODB_DB` | `micro_adventure` | Database name |
| `OLLAMA_URL` | `http://localhost:11434` | Ollama server |
| `OLLAMA_MODEL` | `gemma3:latest` | Model that writes challenges |
| `OLLAMA_VISION_MODEL` | same as `OLLAMA_MODEL` | Model that checks photos |
| `OLLAMA_TIMEOUT_SECONDS` | `30` | Per-request timeout |
| `PHOTO_VERIFIER` | `ollama` | `ollama` or `trusting` |
| `ELEVENLABS_API_KEY` | unset | Enables voice notes (speech to text). Without it people can still write |
| `ELEVENLABS_STT_MODEL` | `scribe_v2` | ElevenLabs speech-to-text model |
| `SENTRY_DSN` | unset | Enables Sentry. Every call to the model becomes a span (`gen_ai.request`) with model, tokens and timings, never the text or photos |
| `SENTRY_ENVIRONMENT` | `development` | Label for the traces (use `production` on Render) |

## Deployment

Render web service from the repo root:

- Build: `pip install poetry==2.5.1 && poetry config virtualenvs.create false && poetry install --no-root --only main`
- Start: `cd src && python manage.py collectstatic --noinput && gunicorn core.wsgi:application --bind 0.0.0.0:$PORT`
- Environment: the variables above, with `MONGODB_URI` pointing at Atlas and `OLLAMA_URL` at the GPU server.
- Run `python src/manage.py migrate` once against Atlas.

In Atlas, allow the service's IP under Network Access.

## Decisions

- **Django models on MongoDB.** `django-mongodb-backend` keeps the kronobot style (models in `domain/`, `Db*Repository`, migrations). Its limits matter here: Django's `transaction.atomic` is not supported, and `Challenge` can only be queried through its walk.
- **Django admin with MongoDB.** Follows the `django-mongodb-backend` configuration guide: custom AppConfigs plus `MIGRATION_MODULES`. WhiteNoise serves the admin's static files in production.
- **Handlers are wired by hand** in `api/wiring.py`, with no dependency-injection library.
- **Dates use UTC.** "Days walked" counts UTC calendar days.
